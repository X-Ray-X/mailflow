# Design

## Context

The mail infrastructure lives in `deploy/mail/` as its own compose project
(`mailflow-mail`) with a pinned `ghcr.io/stalwartlabs/stalwart:v1.1.0`
(linux/arm64). Verification is `deploy/mail/scripts/verify.sh`, which exercises
the specs over real IMAP/SMTP clients. Nothing about that deployment is yet
automated.

## Goals / Non-Goals

**Goals:**

- Every pull request gets a fast structural gate (compose render, service
  inventory, pinned image, published ports).
- Pushing to `main` deploys the mail infrastructure onto the homelab host and
  reports a verdict (ports + tailnet TLS certificate).
- Secrets never enter the repository; they live in the GitHub `production`
  Environment.
- The mail/application boundary stays enforced: nothing in the pipeline
  recreates, upgrades, or resets the mail containers or volumes.

**Non-Goals:**

- CI is a structural gate only, not a full protocol verification; the latter
  stays `scripts/verify.sh` on the host.
- This change does not upgrade or change the pinned Stalwart release.
- This change does not change the mail configuration (domain, hostname, TLS,
  relaying).

## Decisions

### The pipeline runs on the self-hosted runner, not on GitHub-hosted runners

The homelab host already runs a Dockerized GitHub Actions runner
(`/home/radxa/repos/scripts/actions-runner`, labels `docker,radxa`) with the host
docker socket available (Docker-in-Docker). Workflows that touch the mail
infrastructure run there, so `docker compose up -d` lands on the host.

A second runner service was added next to the pre-existing one so the two
repositories are independent:

- the pre-existing runner (unchanged);
- `github-runner-mailflow` — registered for `X-Ray-X/mailflow`, its own data
  directory `runner-data-mailflow`.

### Mail data is mounted at the same path on the host and in the runner

The runner is itself a container. Compose bind mounts are resolved by the host
Docker daemon, so a path that exists only inside the runner (such as the
checkout under `/runner/_work`) mounts a different directory on the host and
disappears when the workspace is cleaned. The host clone
`/home/radxa/repos/mailflow` is therefore mounted into the runner at the same
absolute path, and `MAIL_DATA_DIR` is
`/home/radxa/repos/mailflow/deploy/mail/data`. The deploy refuses to run if
that mount is absent.

The setup listener uses host port `8089` instead of `8080` because the default
is already in use on the deployment host. Only the loopback setup/health
listener moves; the container listener and the public inventory are otherwise
unchanged.

### Workflow files live in the mailflow repository

`.github/workflows/ci.yml`, `deploy.yml` and `pr-agent.yml` are committed to
the repository and run against it.

### Deploy writes `.env` from Environment secrets

The deployment job runs in the `production` Environment and reads
`MAIL_BOOTSTRAP_PASSWORD`, `MAIL_ACCOUNT_ALICE_PASSWORD`,
`MAIL_ACCOUNT_BOB_PASSWORD`. The workflow copies `deploy/mail/.env.example` to
`deploy/mail/.env` (untracked) and injects only the credential fields; everything
else keeps its tracked default. The resulting file is never committed.

### Tailnet verification is SAN-only

The deployment step asserts that the certificate presented for
`mail.mailflow.test` contains `DNS:mail.mailflow.test`. Full validation of that
certificate against the internal CA generated by `bootstrap.sh` stays
`scripts/verify.sh` on the host, because the CA trust store lives on the
clients.

### PR-Agent configuration

The workflow uses `The-PR-Agent/pr-agent@v0.50.0` (pinned: it runs with a
write-scoped `GITHUB_TOKEN` and the production Environment secrets) and the
auto-provided `GITHUB_TOKEN`. The behaviours are controlled by
`github_action_config.*` environment variables.

The model is the free-tier Google AI Studio Gemini, configured as
`gemini/gemini-3-flash-preview`; the provider prefix is required or LiteLLM
routes the request to Vertex AI, which has no credentials here. The job
declares `environment: production` so `GEMINI_API_KEY` is visible.

The job is advisory: the step sets `continue-on-error`, so free-tier quota
exhaustion, provider outages, or a recorded tool error cannot fail the pull
request check. Reviews are a convenience, not a merge gate; CI remains the
only required signal.

A rejected request is not retried: `config.num_retries=0` stops the default
four same-model retries (up to 30s each) that otherwise turn a daily-quota 429
into minutes of spinning, and `github_action_config.fail_on_command_errors=false`
keeps the recorded error from failing the action.
